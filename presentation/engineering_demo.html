The original evaluation describes errors by recorded diagnosis. A separate follow-up examines how the choice between CatBoost and logistic regression changes with the discovery split.

Both models were evaluated on the same 345 specimens from the authors’ technical-validation cohort, after their models and thresholds were fixed using discovery data.

How the discovery specimens were reassigned

CatBoost’s original screening advantage was one fewer false positive at the same sensitivity. This follow-up checked how consistently screening preferred either model across discovery splits.

Each of 20 repetitions randomly reassigned the same 1,050 discovery specimens using a recorded seed. The procedure reserved 210 for assessment, then 210 of the remaining 840 for screening, leaving 630 for training. Both steps preserved approximately the four diagnosis proportions.

Groups were separate within each repetition. Repetitions reused specimens and are not independent trials. The authors’ 345 validation specimens were unused.

Model selection using screening specimens

This follow-up used 630 training specimens instead of 787 and revised the candidates to three logistic settings and two CatBoost depths. The candidate settings stayed fixed across repetitions.

Each threshold retained at least 90% of screening rejection cases. Selection within and between families favored fewer false positives, then higher ROC-AUC. Exact ties between families favored logistic regression.

Application input

An analyst or molecular laboratory researcher can submit raw B-HOT RNA counts through the application. The service uses the saved model without another training run.

The CSV supplied to the service

Each row represents one specimen. The first column is its identifier; the remaining 770 columns contain raw assay counts, including 12 housekeeping targets. The recorded diagnosis is excluded, and the identifier is not a predictor.

The preview shows five measurement columns. The complete input requires all 770. ABCF1 and G6PD are two of the housekeeping targets; IFNG is one of the 758 model targets.

This example comes from the discovery-screening group and has a recorded no-rejection diagnosis. Its use here demonstrates the software.

Local application

The following command starts the service from the project root. The application opens in a separate tab, keeping this explanation available.

On this Mac, use the existing virtual environment:

.venv/bin/python presentation/source/serve_demo.py

With uv installed, the equivalent command is uv run --frozen python presentation/source/serve_demo.py.

From research code to a scoring service

The application needs to reproduce the calculation used during model evaluation. Shared preprocessing, a saved model and its fixed threshold connect the research procedure to the service.

One implementation of specimen preparation

Training and prediction call the same normalization function. The browser collects input and displays results; the service and command line use the shared Python prediction code.

  1. Input validation

    The service checks that every required target is present exactly once and that counts are finite and nonnegative. Invalid input produces an explanation and no predictions.

  2. Specimen normalization

    The shared function calculates log₂(count + 1), then subtracts the mean of the 12 housekeeping log counts. The remaining 758 targets become model inputs.

  3. Model output

    The saved model produces a score. A score at or above its fixed threshold produces a positive rejection flag.

The shared function in the actual source

Both excerpts call normalize_counts. Prediction also supplies the saved schema, which identifies the required targets and their model input order.

Training

features = normalize_counts(raw_counts)

Service and command-line prediction

normalized = normalize_counts(counts, self.schema)
return self.predict_normalized(normalized)

Normalization uses only that specimen’s counts. Models with learned scaling or feature selection fit those steps on training specimens only and retain them with the fitted model.

The same service is available to other software

A batch script or research tool can send a CSV directly to POST /predict. The service applies the same input checks and calculation used by the browser application, then returns a structured response.

Request: one specimen and all 770 counts

This request uses the complete public example shown in the Application tab. The CSV download contains the exact input used for the saved response.

curl http://127.0.0.1:8766/predict \
  -H 'Content-Type: text/csv' \
  --data-binary @no-rejection.csv

Successful response: HTTP 200

The caller receives a result for each specimen. Separate fields describe the numerical result, the threshold decision and the version of the calculation.

Agreement between research results and the service

The recorded check sent all 345 specimens from the authors’ technical-validation cohort through the HTTP service. It compared their results with command-line predictions and the saved research results, using the same model and threshold.

Measurement columns were reordered to check that the service matched targets by name. This comparison tests software consistency; it does not provide another estimate of classifier performance.
